* Adversarial RED
The first production implementation had already demonstrated a GREEN bounded dataset query on a corpus whose outcome index existed before assertions were written. Source review then identified an upgrade hazard: registering a new Tek9 secondary index does not backfill assertions already present in an older durable corpus.

The adversarial contract retained canonical outcome evidence/assertion documents, cleared only =outcome-assertion-outcome=, restarted the expert host, and then queried the dataset.

Observed product behavior on the exact head:
- expert host restart succeeded;
- query status remained =ok=;
- canonical outcome records remained durable;
- the dataset returned no success examples because the new secondary index had no historical postings;
- assertions requiring one example plus truthful truncation/provenance therefore failed.

This is an accepted product RED: without an explicit upgrade migration, an existing #15 corpus can be silently under-selected after deploying the dataset feature.

* Independent lanes
- Common Lisp / Tek9 / SWI-Prolog: RED only in the new dataset upgrade contract after preceding expert contracts passed.
- Python expert policy / adapter / transport lifecycle / launch: GREEN.
- Home Manager expert wiring: GREEN.

* Decision
Use existing Tek9 public =rebuild-index= from the Common Lisp expert host. Gate it with durable versioned migration metadata =meta:index-migration:outcome-assertion-outcome:v1= so the corpus scan happens once during schema upgrade, never per request and not on every ordinary restart. Write the marker only after a successful rebuild; repeating the rebuild after a crash is safe.

No Tek9 repository mutation and no dotfiles mutation are justified by this RED.
