#+title: llm-log expert runtime

* Boundary

This directory is the Common Lisp-owned expert-system runtime for llm-log.

- Tek9 is the durable document/graph KB.
- SWI-Prolog is the rule/inference engine.
- Common Lisp owns lifecycle, typed schemas, bounded fact materialization, Prolog supervision, result validation, and persistence.
- Python owns proxy/capture transport, the versioned client envelope, and the loopback maintenance transport; it does not duplicate expert rules.

The runtime is developed behind black-box and integration contracts under =tests/= and =expert/tests/=. Do not make the Python proxy a second rule engine and do not add an arbitrary Prolog goal operation.

* Executable contract

The expert service runs as:

#+begin_example
llm-log-expert serve --stdio [--data-dir PATH]
#+end_example

with one JSON object per input/output line. One service process owns one Tek9 environment and one persistent supervised SWI-Prolog worker for its lifetime.

Public operations are finite and typed. Current operations include request observation/classification, bounded classification history, request/task usage accounting, outcome evidence/history/dataset queries, and health. Untrusted strings are data, never executable Prolog terms.

* Live maintenance boundary

When =llm-log serve= is configured with =--expert-service-bin=, that proxy process owns the expert child and may expose a separate maintenance listener on literal loopback only. The default is =127.0.0.1:8788=; =--expert-admin-port 0= disables it.

The maintenance surface is deliberately smaller than the private stdio protocol:
- =GET /health=;
- =POST /query= for declared read-only expert operations only;
- =POST /backfill-event= for one typed historical capture replay.

Do not start a second =llm-log-expert= process against the live Tek9 directory for inspection or backfill.

Operator commands use the loopback maintenance listener:

#+begin_src sh
llm-log expert backfill --source ~/.llm-proxy/data/events.jsonl

llm-log expert query query_outcome_dataset \
  --payload '{"outcome":"success","scope":"request","limit":64}'

llm-log expert export-dataset \
  --source ~/.llm-proxy/data/events.jsonl \
  --output ./datasets/success.jsonl \
  --outcome success \
  --scope request
#+end_src

Historical replay reuses stable capture identities and is idempotent. Request-level provider token usage can be backfilled without fabricating task or pricing state. Provider transport evidence is opt-in and weak; HTTP success alone never means task success.

Outcome dataset queries are cursor-paginated while each expert request remains bounded. Dataset export joins the provenance-complete expert result back to the exact immutable raw capture and writes a SHA-256 sidecar manifest.

* Mutable state

The reusable llm-log default mutable state root is:

#+begin_example
~/.llm-proxy/
#+end_example

Expert runtime state therefore defaults below =~/.llm-proxy/expert/=.

This is a default, not a hardcoded machine path. Standalone configuration/CLI and Home Manager =services.llm-log.dataDir= may override the root. Consumer configuration such as dotfiles may point it at a personal corpus directory without changing the reusable llm-log default. No mutable database state belongs in the Nix store.

* Packaging

Tek9's reusable Nix/ASDF package support is merged on Tek9 =master= and the llm-log flake consumes that immutable merged revision.

The llm-log flake exposes:
- =llm-log= — Python capture/proxy package;
- =llm-log-expert-lib= — Common Lisp ASDF system closure;
- =llm-log-expert= — executable SBCL + Tek9 + SWI-Prolog expert service;
- =expert-service-contract= — packaged black-box contract check.

The executable receives its immutable packaged =worker.pl= path through =LLM_LOG_PROLOG_WORKER=. This is packaging metadata, not user state. A source checkout may fall back to the ASDF-relative worker path.

No developer-local Quicklisp checkout is required and no mutable database state is written into the Nix store.
