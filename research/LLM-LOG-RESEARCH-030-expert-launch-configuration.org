#+title: LLM-LOG-RESEARCH-030 — Expert launch and configuration contract
#+startup: overview

* Scope
Issue: https://github.com/lost-rob0t/llm-log/issues/10
PR: https://github.com/lost-rob0t/llm-log/pull/24

Bounded Auto-ARADR decision for making the already-proven Common Lisp expert service reachable from ordinary Python capture-proxy launches without moving expert semantics into Python. This document supersedes conflicting zero-Python prose in #8/#10/#20 for this boundary: Python remains transparent HTTP/SSE/WebSocket capture/transport; Common Lisp owns expert runtime, typed expert objects, Tek9 access, bounded fact materialization, SWI-Prolog supervision and result validation.

* Analyze
The active branch already packages =llm-log-expert= with SBCL, Tek9 and SWI-Prolog. =SubprocessExpertPlane= owns a long-lived child and the aiohttp lifecycle starts/closes it. However =llm_log/cli.py= never constructs that adapter and the Home Manager module has no expert-plane options. Therefore =llm-log serve=, including the systemd user service generated by Home Manager, cannot currently enable the expert plane even though the substrate is executable.

The consumer dotfiles currently pins an older stable llm-log revision and keeps raw capture at =~/Documents/AI/proxy=. That consumer remains untouched until the upstream launch contract is proven.

* Research
The smallest authority-preserving integration is configuration of the existing subprocess boundary, not a second Python expert implementation and not a second independent systemd daemon.

Python may know only how to launch the declared Common Lisp service command and where its mutable expert state lives. The child continues to speak the versioned JSON-lines protocol and Common Lisp remains the only Tek9/SWI-Prolog authority.

Mutable expert state must remain separate from immutable raw capture evidence. The reusable default expert state is =~/.llm-proxy/expert=. Home Manager may override it explicitly. The raw capture default/path is not changed by this slice.

Credentials are neither expert configuration nor expert state. The launch contract must not accept or serialize provider credentials, and no credential value may enter Nix derivation text.

* Design
** Python CLI contract
Add explicit =llm-log serve= options:
- =--expert-service-bin PATH= — enables the concrete expert adapter using this executable;
- =--expert-data-dir PATH= — mutable Tek9/expert state, default =~/.llm-proxy/expert=;
- =--require-expert-plane= — explicit fail-closed policy; without it the existing fail-open policy remains authoritative.

When no expert service binary is configured, behavior is unchanged and no expert child is launched. When configured, Python constructs exactly one =SubprocessExpertPlane= argv vector:

#+begin_example
<expert-bin> serve --stdio --data-dir <expert-data-dir>
#+end_example

No shell interpolation and no arbitrary Prolog goal surface are introduced.

** Home Manager/systemd contract
Extend =services.llm-log= with an =expert= submodule:
- =expert.enable=, default false;
- =expert.package=, default =self.packages.${system}.llm-log-expert=;
- =expert.dataDir=, default =~/.llm-proxy/expert= using the configured home directory;
- =expert.require=, default false.

When enabled, the existing =llm-log.service= systemd user unit passes the packaged expert executable and expert data directory to the Python transport process. The expert remains a supervised child of the proxy, matching the already-tested adapter lifecycle. No duplicate standalone daemon is created.

** Non-Nix path
The same Python CLI flags are the ordinary non-Nix integration path. A source-installed Common Lisp service may be supplied through =--expert-service-bin= once its ASDF dependencies (Tek9, JSOWN) and =swipl= are available. =expert/README.org= documents the direct service command and the proxy launch form. Nix remains the reproducible packaging path; non-Nix is not allowed to rely on hidden machine-specific paths.

** Failure semantics
- expert disabled: transport behavior unchanged;
- expert configured but unavailable: existing default fail-open behavior;
- expert configured + =--require-expert-plane=: existing fail-closed behavior before upstream contact;
- expert startup/health failure never exposes child stderr or credentials in proxy responses;
- no implicit replay of ambiguous expert exchanges.

* Tek9 schema and database boundary
No Tek9 mutation is required. This slice changes only launch/configuration of the already-proven Common Lisp host. Existing public Tek9 package/API and bounded primary-key retrieval remain sufficient.

Expert state remains durable Tek9 state beneath the configured expert directory. Raw capture evidence remains separately owned by the Python recorder and is never rewritten into Tek9 by launch configuration.

* Adversarial review
- Do not create a Python rule engine, classifier replacement, pricing table or outcome policy.
- Do not expose a generic command string that is shell-evaluated; use an executable path plus fixed declared argv.
- Do not start a second systemd expert daemon while the proxy also owns a child; one lifecycle authority avoids duplicate writers and ambiguous recovery.
- Do not derive expert mutable-state paths from the raw capture path implicitly. The user's =~/Documents/AI/proxy= raw corpus must remain unchanged unless the consumer explicitly opts into a separate expert path later.
- Do not put provider credentials, authorization headers or secret environment values in Nix options/derivations.
- Do not claim Home Manager/non-Nix GREEN from source inspection alone.

* Exact RED-first acceptance
Before production mutation, add and execute a contract against the untouched pre-implementation head proving:
1. =llm-log serve --help= lacks the expert launch options or parser rejects them;
2. a CLI construction test cannot obtain a configured =SubprocessExpertPlane= from the current CLI path;
3. Home Manager evaluation with =services.llm-log.expert.enable = true= fails because the option does not exist;
4. existing expert integration and HTTP/WebSocket contracts remain GREEN in the same hosted run.

The RED is valid only if execution reaches these missing configuration surfaces. Syntax/import/Nix-fixture failures do not count.

After RED, production acceptance requires the unchanged contract to prove:
- CLI enables one concrete subprocess adapter using fixed argv and the configured data directory;
- CLI default leaves the expert plane disabled;
- =--require-expert-plane= maps to the existing fail-closed policy;
- Home Manager evaluation emits the existing proxy systemd service with the packaged =llm-log-expert= executable and separate expert data directory;
- no standalone second expert systemd writer is created;
- existing adapter/transport and CL/Tek9/SWI contracts remain GREEN.

* Decision
Proceed with this launch/configuration slice on =rage/10-expert-runtime-red= behind a fresh executed RED. Do not mutate dotfiles or Tek9 in this slice. PR #5 remains a separate configuration transaction and is not imported into #24.
